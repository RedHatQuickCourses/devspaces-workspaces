Understanding Devfile Structure

A Devfile is a YAML-based configuration file that follows the Devfile 2.x specification to describe a complete development environment. It defines the tools, runtimes, commands, projects, and automation required to develop an application consistently across different environments.

Key Components of a Devfile:

Projects

Defines the source code repositories that should be cloned into the workspace when it starts.

Components

Defines the containers, Kubernetes resources, plugins, or volumes required by the development environment, such as application runtimes, databases, and supporting services.

Commands

Defines reusable actions such as build, run, debug, and test operations that can be executed within the workspace.

Events

Associates commands with workspace lifecycle events to automate tasks during workspace startup, initialization, or shutdown.

An example Devfile, defining a development environment for a simple Node.js application that communicates with a PostgreSQL database is provided below:

schemaVersion: 2.2.0

schemaVersion: 2.2.0

metadata:                           (1)
  name: nodejs-sample-app
  version: 1.0.0
  description: Devfile for a sample Node.js application
  icon: https://raw.githubusercontent.com/devfile-samples/devfile-stack-icons/main/node-js.svg
  tags:
    - Node.js
    - Express

projects:                           (2)
  - name: nodejs-app
    source:
      type: git
      location: https://github.com/some-repository/nodejs-app.git
      branch: main

components:

  - name: nodejs                    (3)
    container:
      image: registry.redhat.io/devspaces/udi-rhel9:3.27
      memoryLimit: 1Gi
      memoryRequest: 512Mi
      cpuLimit: "1"
      cpuRequest: 250m
      mountSources: true

      endpoints:                    (5)
        - name: app
          targetPort: 3000
          exposure: public
          protocol: http
          attributes:
            discoverable: true
            urlRewriteSupported: true

      volumeMounts:                 (4)
        - name: node-modules
          path: /projects/node_modules

  - name: postgres-db               (6)
    container:
      image: quay.io/sclorg/postgresql-15-c9s
      memoryLimit: 1Gi
      memoryRequest: 512Mi

      endpoints:
        - name: postgres
          exposure: internal
          targetPort: 5432
          attributes:
            discoverable: true

      env:
        - name: POSTGRESQL_USER
          value: user

        - name: POSTGRESQL_PASSWORD
          value: password

        - name: POSTGRESQL_DATABASE
          value: devdb

      volumeMounts:
        - name: db-data
          path: /var/lib/pgsql/data

  - name: node-modules              (9)
    volume:
      size: 1Gi

  - name: db-data                   (9)
    volume:
      size: 1Gi

commands:                           (7)

  - id: install
    exec:
      component: nodejs
      commandLine: npm install
      workingDir: /projects/nodejs-app

    group:
      kind: build
      isDefault: true

  - id: run
    exec:
      component: nodejs
      commandLine: npm run dev
      workingDir: /projects/nodejs-app

    group:
      kind: run
      isDefault: true

  - id: test
    exec:
      component: nodejs
      commandLine: npm test
      workingDir: /projects/nodejs-app

    group:
      kind: test
      isDefault: true

  - id: cleanup
    exec:
      component: nodejs
      commandLine: npm run clean
      workingDir: /projects/nodejs-app

events:                             (8)

  preStart:
    - install

  postStop:
    - cleanup
1 Devfile metadata. Name, description, tags, and an icon declaration.
2 Project details and location of Git repository
3 Container image used for the development environment. In production environments, it is recommended to use the Red Hat Universal Developer Image (UDI) provided with OpenShift Dev Spaces.
4 Mount data volumes inside the container. These reference volume names are declared in the volumes section.
5 Network endpoints to be exposed in the workspace.
6 Declaration of the PostgreSQL database container, along with volume mounts, resource limits, and some environment variables used by the container.
7 These commands can be executed manually or through IDE integrations such as Tasks in Visual Studio Code - Open Source.
8 Workspace lifecycle events that automatically invoke predefined commands during initialization, startup, or shutdown.
9 Persistent volume declarations used by containers to store application dependencies and database data across workspace restarts.
Red Hat OpenShift Dev Spaces supports many container images for defining development environments. However, for enterprise environments, Red Hat recommends using the Universal Developer Image (UDI) or custom images built from Red Hat Universal Base Images (UBI) to ensure compatibility, supportability, and security updates.
Custom development images must satisfy the requirements of the selected IDE. If required dependencies are missing, the IDE may fail to start. When building custom images, consider extending the Universal Developer Image (UDI) provided with OpenShift Dev Spaces.
